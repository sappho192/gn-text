# gn-text 리포지토리 분석 및 개선 제안

- 문서 작성일: 2026-08-25
- 분석 기준 커밋: `a7dda11`
- 분석 대상 브랜치: `main`
- 분석 범위: 애플리케이션 코드, 테스트, 문서, GitHub Actions, GoReleaser 및 Chocolatey 구성

## 1. 요약

`gn-text`는 GeekNews의 RSS, 토픽 본문 및 댓글을 터미널에서 읽을 수 있도록 구현한 Go 기반 TUI 애플리케이션입니다. 파일 수가 적고 `main.go`, `parser.go`, `web.go`, `ui.go`의 책임이 비교적 명확하게 나뉘어 있어서 전체 동작을 이해하기 쉽습니다. RSS와 HTML 파서의 단위 테스트도 충실한 편입니다.

다만 실제 사용자 동작에서는 다음 문제가 프로그램 종료, UI 정지 또는 잘못된 기사 선택으로 이어질 수 있습니다.

1. 기사 추출 라이브러리가 네트워크 오류를 반환하지 않고 프로그램을 종료할 수 있습니다.
2. 새로고침 처리 중에 이미 실행 중인 TUI 이벤트 루프를 다시 실행합니다.
3. 모든 네트워크 요청이 UI 이벤트 처리 흐름에서 동기적으로 실행되며, timeout과 HTTP 상태 코드 검사가 없습니다.

따라서 새로운 기능을 추가하기 전에 런타임 안정성과 테스트 가능성을 우선적으로 개선하는 편이 좋습니다.

## 2. 확인한 장점

### 2.1 구조가 단순하고 책임 구분이 명확합니다.

- `main.go`는 초기화와 실행을 담당합니다.
- `parser.go`는 RSS와 GeekNews HTML을 구조화된 데이터로 변환합니다.
- `web.go`는 HTTP 요청과 화면 표시용 문자열 변환을 담당합니다.
- `ui.go`는 tview 위젯과 키 입력 및 화면 전환을 담당합니다.

현재 규모에서는 이러한 구성이 코드를 탐색하고 변경하기에 충분히 단순합니다.

### 2.2 파서와 한국어 문자열 처리에 대한 기본 검증이 마련되어 있습니다.

RSS, 댓글, 토픽 본문, URL, 한국어 HTML 정리 및 CJK 표시 폭에 대한 fixture 기반 테스트가 존재합니다. 분석 시점의 함수별 커버리지에서 주요 파서 함수는 대부분 90% 이상의 statement coverage를 기록했습니다.

### 2.3 배포 대상 운영체제에 대한 빌드 구성이 마련되어 있습니다.

GoReleaser는 Linux, macOS 및 Windows의 amd64와 arm64 빌드를 생성하도록 구성되어 있습니다. Homebrew와 Chocolatey 배포 경로도 함께 정의되어 있습니다.

### 2.4 현재 GeekNews RSS 형식은 기존 RSS 파서의 핵심 가정과 호환됩니다.

2026-08-24에 확인한 [GeekNews RSS](https://news.hada.io/rss/news)는 Atom `entry`와 `rel="alternate"` 토픽 링크를 계속 제공하고 있었습니다. 당시 feed에는 50개의 entry가 있었고, 첫 entry의 토픽 링크도 현재 파서가 기대하는 `https://news.hada.io/topic?id=...` 형식이었습니다.

## 3. 우선 개선 사항

### 3.1 최우선: 기사 로딩 실패가 프로그램 전체를 종료할 수 있습니다.

`ui.go`의 `getArticleTextFromLink()`는 `articletext.GetArticleTextFromUrl()`이 오류를 반환할 것으로 가정합니다.

```go
func getArticleTextFromLink(url string) string {
	article, err := articletext.GetArticleTextFromUrl(url)
	if err != nil {
		fmt.Printf("기사 파싱 실패 %s, %v\n", url, err)
		return ""
	}
	return article
}
```

그러나 현재 사용하는 `github.com/gelembjuk/articletext` 버전은 URL 요청이나 HTML 파싱 중에 오류가 발생하면 내부에서 `log.Fatal()`을 호출합니다. 따라서 네트워크 장애나 지원하지 않는 문서를 만났을 때 위의 오류 처리 코드로 돌아오지 않고 프로세스가 종료될 수 있습니다.

권장 개선 방법은 다음과 같습니다.

- 자체 `http.Client`로 문서를 내려받고, Reader를 받는 추출 API에 전달해야 합니다.
- 장기적으로는 `context.Context`와 오류 반환을 정상적으로 지원하는 추출 라이브러리로 교체해야 합니다.
- 기사 추출 실패 시 TUI를 유지하고, 브라우저에서 원문을 열 수 있다는 안내를 표시해야 합니다.
- TUI 실행 중에는 `fmt.Printf()`나 `log.Fatal()`로 터미널 화면을 훼손하거나 프로세스를 종료하지 않아야 합니다.

관련 위치는 `ui.go:152`와 `go.mod:8`입니다. 의존성의 종료 동작은 [articletext의 GetArticleTextFromUrl 구현](https://github.com/gelembjuk/articletext/blob/bc7a97ba132a/exported.go#L34-L40)에서도 확인할 수 있습니다.

### 3.2 최우선: 새로고침이 이벤트 루프를 중첩 실행합니다.

`ui.go:75-83`의 새로고침 처리에서는 새로운 목록을 만든 뒤 `Application.Run()`을 다시 호출합니다.

```go
currentArticles = newArticles
pages.AddPage("homepage", refreshedList, true, false)
app.SetRoot(refreshedList, true).Run()
```

애플리케이션은 이미 `main.go:44`에서 실행 중이므로, 키 입력 처리 함수에서 `Run()`을 다시 호출하면 이벤트 루프와 화면 입력 처리가 중첩될 수 있습니다. 새로고침을 반복할수록 이러한 문제가 누적될 가능성도 있습니다.

또한 `currentArticles`만 새로운 데이터로 변경되고, 선택 위치를 읽을 때 사용하는 `list` 변수는 이전 목록을 계속 참조합니다. RSS 항목의 수나 순서가 달라지면 화면에서 선택한 기사와 실제로 열리는 기사가 일치하지 않을 수 있습니다.

권장 개선 방법은 다음과 같습니다.

- `Application.Run()`은 `main.go`에서 한 번만 호출해야 합니다.
- 새로고침 시 기존 `tview.List`의 항목을 다시 채우거나, 현재 목록 참조를 포함한 애플리케이션 상태를 함께 교체해야 합니다.
- 비동기 작업의 결과는 `Application.QueueUpdateDraw()`에서 화면에 반영해야 합니다.
- 새로고침 실패를 무시하지 않고 기존 목록을 유지하면서 오류를 화면에 표시해야 합니다.

### 3.3 최우선: 네트워크 요청이 TUI를 무기한 정지시킬 수 있습니다.

`web.go:25-37`의 `fetchWebpage()`는 기본 `http.Get()`을 사용합니다.

현재 구현에는 다음 보호 장치가 없습니다.

- 요청 timeout이 없습니다.
- HTTP 상태 코드 검사가 없습니다.
- 응답 본문의 최대 크기 제한이 없습니다.
- 요청을 취소할 `context.Context`가 없습니다.
- 재시도 정책과 사용자에게 표시할 로딩 상태가 없습니다.

댓글, 기사 및 새로고침 요청도 키 입력 처리 흐름에서 동기적으로 실행되므로, 응답이 늦으면 전체 TUI가 정지합니다. 또한 서버가 403이나 500 상태와 함께 정상적인 HTML 문서를 반환하면, 댓글 파서는 오류를 감지하지 못하고 해당 응답을 "댓글이 없음"으로 해석할 수 있습니다.

권장 개선 방법은 다음과 같습니다.

- 하나의 공유 `http.Client`를 만들고 명시적인 timeout을 설정해야 합니다.
- 2xx 이외의 상태 코드는 본문을 파싱하기 전에 오류로 처리해야 합니다.
- `io.LimitReader`를 사용하여 RSS와 HTML 응답 크기를 제한해야 합니다.
- 네트워크 요청을 goroutine에서 실행하고, 완료 결과만 TUI 이벤트 루프에 전달해야 합니다.
- 사용자가 다른 화면으로 이동하면 진행 중인 요청을 취소해야 합니다.
- 로딩 중, 재시도 중 및 최종 실패 상태를 화면에 구분하여 표시해야 합니다.

### 3.4 높음: 빈 목록에서 키를 누르면 panic이 발생할 수 있습니다.

`ui.go:70`, `ui.go:73`, `ui.go:104` 및 `ui.go:106`은 목록 길이를 확인하지 않고 다음 형태로 기사를 선택합니다.

```go
articles[list.GetCurrentItem()]
```

`parser_test.go`는 빈 RSS를 정상 입력으로 허용하고 있습니다. 따라서 GeekNews가 일시적으로 빈 feed를 제공하거나 향후 필터 기능이 빈 결과를 만들면, `l`, 오른쪽 화살표, Space 또는 `c` 입력으로 panic이 발생할 수 있습니다.

빈 목록에서는 "표시할 기사가 없습니다"라는 상태를 보여주고, 선택 항목이 필요한 동작을 수행하지 않아야 합니다. 선택 인덱스가 `0 <= index < len(articles)` 범위에 있는지도 공통 함수에서 검사하는 편이 좋습니다.

### 3.5 높음: 깊은 댓글의 생략 표시가 실행될 수 없습니다.

`parser.go:116-120`은 깊이가 10보다 큰 댓글을 파싱 결과에서 제거합니다. 반면 `web.go:175-178`은 깊이가 10보다 큰 댓글에 `[...]`을 표시하려고 합니다.

파서에서 해당 댓글을 이미 제거했으므로, 포맷 함수의 생략 표시 분기는 실행될 수 없습니다. 이는 `docs/geeknews-spec.md`에 기재된 "10단계보다 깊은 댓글은 `[...]`로 표시한다"라는 동작과도 다릅니다.

다음 방법 중 하나로 동작을 명확히 정의해야 합니다.

- 파서가 깊은 하위 트리를 하나의 생략 항목으로 변환해야 합니다.
- 모든 댓글을 유지하되 포맷 함수가 표시 깊이를 제한하고 생략 여부를 계산해야 합니다.

깊이 10, 깊이 11 및 여러 개의 깊은 하위 댓글을 포함하는 경계 테스트도 필요합니다.

### 3.6 보통: 외부 텍스트가 tview 스타일 태그로 해석될 수 있습니다.

`ui.go:161-178`은 기사와 댓글 화면에서 `SetDynamicColors(true)`를 사용합니다. GeekNews나 외부 기사에서 가져온 문자열에 `[red]` 또는 `[-]` 같은 내용이 포함되면, 일반 텍스트가 아니라 tview 스타일 태그로 처리될 수 있습니다.

애플리케이션이 직접 추가하는 색상 태그와 외부 데이터를 구분하고, 외부 제목·본문·댓글에는 `tview.Escape()`를 적용해야 합니다. 또는 외부 콘텐츠를 표시하는 TextView에서는 dynamic color를 사용하지 않는 방법도 적절합니다.

### 3.7 보통: URL 검증과 브라우저 실행 오류 처리가 부족합니다.

`ui.go:138`은 `strings.HasPrefix(externalLink, "http")`만으로 기사 URL을 검사합니다. 이 검사는 유효한 URL과 허용 가능한 scheme을 정확하게 보장하지 않습니다. `ui.go:224`에서는 브라우저 실행 오류도 무시합니다.

`net/url`로 URL을 파싱하고 `http`와 `https` scheme만 허용해야 합니다. `exec.Command().Start()`의 오류도 사용자에게 반환해야 합니다. 특히 Windows에서는 외부 입력 URL을 `cmd /c start`로 전달하므로, 운영체제별 URL 열기 구현과 인자 처리 방법을 별도로 검증하는 편이 안전합니다.

## 4. 테스트 개선 사항

분석 시점에 실행한 검증 결과는 다음과 같습니다.

| 검증 항목 | 결과 |
|---|---|
| `go test ./...` | 통과했습니다. |
| `go test -race ./...` | 통과했습니다. |
| `go vet ./...` | 통과했습니다. |
| `gofmt -d ...` | 차이가 없습니다. |
| `go mod tidy -diff` | 차이가 없습니다. |
| `go mod verify` | 모든 모듈이 검증되었습니다. |
| Linux amd64 교차 빌드 | 통과했습니다. |
| Windows amd64 교차 빌드 | 통과했습니다. |
| macOS arm64 빌드 | 통과했습니다. |
| 전체 statement coverage | 42.1%입니다. |

전체 커버리지는 42.1%이지만, 파서 함수는 대부분 90% 이상이고 UI, 네트워크 및 기사 추출 함수는 0%입니다. 따라서 단순히 전체 수치를 높이기보다 사용자 동작 경로를 우선적으로 검증해야 합니다.

우선 추가할 테스트는 다음과 같습니다.

1. 새로고침을 여러 번 수행해도 이벤트 루프가 재실행되지 않는지 검증해야 합니다.
2. 새로고침 전후에 화면의 선택 항목과 열리는 기사가 일치하는지 검증해야 합니다.
3. 빈 기사 목록에서 모든 키 입력이 panic 없이 처리되는지 검증해야 합니다.
4. `httptest.Server`를 사용하여 404, 403, 500, timeout 및 큰 응답을 검증해야 합니다.
5. 기사 추출 실패가 프로세스를 종료하지 않고 오류 상태로 변환되는지 검증해야 합니다.
6. 깊이 10과 11의 댓글 표시를 검증해야 합니다.
7. 긴 URL이나 공백 없는 긴 단어도 지정한 표시 폭을 넘지 않는지 검증해야 합니다.
8. 외부 콘텐츠에 tview 스타일 태그 형태의 문자열이 있어도 원문 그대로 표시되는지 검증해야 합니다.

DOM fixture 기반 단위 테스트와 별도로, GeekNews의 현재 selector 호환성을 정기적으로 확인하는 비차단 canary도 유용합니다. 외부 사이트 장애가 일반 pull request 테스트를 불안정하게 만들지 않도록, 이 검사는 단위 테스트와 분리해야 합니다.

## 5. CI 및 릴리스 개선 사항

### 5.1 테스트와 릴리스의 Go 버전 정책을 통일해야 합니다.

`.github/workflows/test.yml`은 `go-version: 1.x`를 사용하고, `.github/workflows/release.yml`은 Go 1.21을 사용합니다. 테스트 환경과 실제 릴리스 환경이 다르면 최신 Go에서는 통과하지만 릴리스 버전에서는 실패하는 변경을 놓칠 수 있습니다.

최소 지원 버전과 주력 개발 버전을 명시하고, 필요한 경우 두 버전을 행렬로 검사해야 합니다. 릴리스 빌드는 검증한 버전 중 하나와 일치해야 합니다.

### 5.2 태그 릴리스 전에 테스트 gate를 실행해야 합니다.

현재 릴리스 워크플로는 태그가 푸시되면 GoReleaser를 바로 실행합니다. 해당 태그가 `main` 브랜치 CI를 통과했는지 릴리스 워크플로 자체에서는 보장하지 않습니다.

GoReleaser와 Chocolatey 배포 전에 최소한 다음 검사를 수행해야 합니다.

- `go test ./...`를 실행해야 합니다.
- `go vet ./...`를 실행해야 합니다.
- `gofmt` 차이가 없는지 검사해야 합니다.
- 지원 운영체제 빌드가 성공하는지 검사해야 합니다.

검증 job이 통과한 뒤에만 GitHub Release, Homebrew 및 Chocolatey 배포 job을 실행하도록 의존 관계를 구성해야 합니다.

### 5.3 GitHub Actions 권한을 job 단위로 제한하는 편이 좋습니다.

현재 `contents: write` 권한이 워크플로 전체에 적용됩니다. GitHub Release를 생성하는 job에만 쓰기 권한을 부여하고, Chocolatey job과 일반 테스트 job에는 읽기 권한만 부여하는 편이 안전합니다.

사용하는 GitHub Actions 버전도 정기적으로 갱신하고, 릴리스 보안을 더 강화하려면 commit SHA 고정을 검토할 수 있습니다.

## 6. 문서 개선 사항

`docs/geeknews-spec.md`는 버전 1.0.0의 최종 명세로 표시되어 있습니다. 그러나 현재 Git tag는 v0.1.2까지 존재하며, 다음 항목은 명세에 기재되어 있지만 구현되어 있지 않습니다.

- loading indicator와 상태 표시줄이 구현되어 있지 않습니다.
- context 기반 취소와 timeout이 구현되어 있지 않습니다.
- 기사 추출 fallback chain이 구현되어 있지 않습니다.
- 메모리 및 디스크 cache가 구현되어 있지 않습니다.
- `Enter`, `Tab`, `o`, `n`, `?` 키 동작이 구현되어 있지 않습니다.
- 자동 재시도와 지수 backoff가 구현되어 있지 않습니다.

명세를 다음과 같이 분리하는 편이 좋습니다.

- 현재 구현을 설명하는 MVP 사양을 별도로 유지해야 합니다.
- 향후 구현 항목은 roadmap 문서로 이동해야 합니다.
- 각 항목에 `Implemented`, `Planned`, `Post-MVP` 상태를 표시해야 합니다.
- README에는 실제로 사용할 수 있는 키와 알려진 제한 사항만 기재해야 합니다.

## 7. 권장 작업 순서

다음 순서로 개선하면 위험도가 높은 문제부터 제거하면서 테스트 가능한 구조를 만들 수 있습니다.

1. 기사 추출 라이브러리의 `log.Fatal()` 경로를 제거해야 합니다.
2. 애플리케이션 상태를 구조체로 모으고 새로고침 중 `Run()` 재호출을 제거해야 합니다.
3. timeout, 상태 코드 검사, 크기 제한 및 context를 지원하는 HTTP 계층을 도입해야 합니다.
4. 네트워크 작업을 비동기로 실행하고 로딩·오류 상태를 TUI에 표시해야 합니다.
5. 빈 목록과 깊은 댓글의 경계 동작을 수정해야 합니다.
6. 외부 텍스트 escaping과 URL 검증을 추가해야 합니다.
7. UI, 네트워크 및 기사 추출 테스트를 보강해야 합니다.
8. 릴리스 전에 자동 검증 gate를 추가해야 합니다.
9. 최종 명세와 roadmap을 현재 구현 상태에 맞게 분리해야 합니다.

## 8. 완료 기준 제안

우선 개선 작업은 다음 조건을 모두 충족할 때 완료된 것으로 판단할 수 있습니다.

- 네트워크와 기사 추출 실패가 프로그램 종료로 이어지지 않아야 합니다.
- 사용자가 반복해서 새로고침해도 이벤트 루프가 하나만 유지되어야 합니다.
- 모든 네트워크 요청에 timeout과 취소 경로가 있어야 합니다.
- 빈 목록에서 모든 키 입력이 안전하게 처리되어야 합니다.
- 깊은 댓글의 생략 표시가 명세와 일치해야 합니다.
- UI 및 네트워크 핵심 동작에 회귀 테스트가 있어야 합니다.
- 태그 릴리스 전에 테스트와 정적 검사가 자동으로 통과해야 합니다.
